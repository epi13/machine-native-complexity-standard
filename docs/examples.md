# Examples

## MNCS implementation evidence

- **minimal** — accepted MNCS-L1 identity transform.
- **http-chunked-decoder** — compact MNCS-L4 conceptual parser bundle grounded in the
  bounded research task, without copied transcripts.
- **rejected-candidate** — valid L4 rejection because benefit is below threshold.
- **repair-workflow** — L3 exception-driven repair with a compact structural witness.
- **structural-provider** — L3 provider-neutral result and provider registration.
- **validator-rule-engine** — L3 readable versus table-driven gate aggregation with
  differential and mutation evidence; it does not claim the validator itself is
  machine-native.
- **legacy-0.1** — explicit frozen-schema compatibility and reduced-assurance report.

## MNCDS development evidence

- **mncds-d4** — cumulative D4 process record with bounded generation, two candidates,
  a rejected alternative, protected holdout, independent evaluation, MNCS binding,
  tested rollback, regeneration drill, monitoring thresholds, and retirement triggers.

Run all examples with:

```bash
./scripts/verify-examples
```

Run the deterministic process corpus with:

```bash
PYTHONPATH=src ./scripts/run-mncds-corpus
```

The example evidence files are illustrative records, not proof that the toy
implementations or development processes are suitable for production.

The rejected MNCS candidate is valid evidence with a computed FAIL. The repair example
retains the failed source and compact witness, changes the candidate hash, bounds repair
count, and performs a full reevaluation without cross-hash result reuse. The MNCDS
example remains a draft-process demonstration and does not make RFC 0004 accepted.
